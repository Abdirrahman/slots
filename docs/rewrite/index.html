Keep the browser delivery. Rewrite the driving contract, track model, content tools, and game flow around a fast, tactical household slot racer inspired by Grooverider.

The current project proves that races and private rooms work. The next version needs a coherent racing experience, authored spectacle, and a production pipeline capable of building a whole game.

Recommendation. Use TypeScript + Three.js/WebGL2 + Blender/glTF, with a pure, fixed-step lane simulation. Build offline first, prove one finished track, then produce the full content set and reconnect private online play. A new engine alone will not fix the missing game design or map pipeline.

Planning assumptions

Desktop browsers first. Keyboard and gamepad. Single-player, two-player local split-screen, and existing four-racer private online play are the proposed complete-release scope. Online is a modern extension; it is not being claimed as a PS2 feature.

No platform or mode preference was supplied before drafting. Existing browser/private-room intent comes from docs/game-design.md. The engine decision changes if desktop distribution becomes the primary requirement.

Definition of complete

Five original household environments, ten circuit layouts, twelve distinct car bodies, three voltage tiers, a championship, quick race, practice/time trial, local split-screen, private online rooms, finished audio, and tested browser delivery.

These are proposed production counts, not verified counts from Grooverider. Forty-plus reference cars are not a prerequisite for matching its mechanics. This report plans the rewrite; it does not implement it.

01

Repository diagnosis

A sound prototype.
An incomplete game contract.

The most consequential problems are content assumptions and missing play systems. The deterministic simulation and room lifecycle are useful foundations, even though much of their implementation must change.

Standards & implementation

Strict TypeScript, deliberate module seams, swept interaction ordering, input buffering, reconnect handling, and a reproducible Blender pipeline are strengths. Coupled content, limited track frames, cosmetic-only car assignment, and fragile asset/build failure paths are the main engineering findings.

Specification & reference fit

The old specification deliberately excluded progression, campaign, tutorial, and unlocks. Its auto-driving rules, three-item set, and single implemented map establish a narrower game. Passing tests confirm those rules, rather than demonstrating reference parity.

P1 · product Four car models share one gameplay profile

Room.startRace assigns this.carProfile to every seat. createCar chooses its model by array index, not the racer's selection. There is no player-facing car selection command. The documented four profiles therefore do not exist as selectable gameplay choices.

P1 · geometry The track representation excludes full stunt geometry

Lane offsets use a horizontal XZ tangent plus bank. Bank is limited to ±45°. The camera also derives its forward direction from yaw; surfaceUp omits pitch. This cannot express a continuous full loop, inverted track, or corkscrew, despite those being permitted in the design document. The surface normal is also inconsistent with pitched car orientation on ordinary climbs.

Rewrite action: author a continuous position and orientation frame along the route, compile quaternion frames and lane lengths, and give track mesh, car pose, camera, effects, and collision authoring the same source.

P1 · reference gap Acceleration and risk are largely chosen for the player

CarInput only carries lane change and boost. Normal speed automatically targets the safe corner speed, so the main overspeed decision is whether to boost. Direct PS2 gameplay observation indicates player-controlled acceleration; exact button mapping and brake behavior are still unverified. The current auto-driving rule is a material parity risk.

Rewrite action: verify controls in the first research gate, then prototype analog acceleration, corner-risk feedback, and lane timing together. Keep auto-throttle as an explicitly labelled assist if it improves accessibility. Do not treat a guessed brake control as a historical fact.

P1 · scope gap Core reference systems are absent or substitutes

The code has boost, shield, and a randomized rear hazard. It has no explicit lane-lock effect, no selectable voltage tiers, no championship or unlock save, and no two-player local renderer. Blocked lane changes replace a fuller barging contract. Similar names do not establish equivalent behavior.

Rewrite action: create an observed mechanic matrix and an executable rule for every required interaction. Treat lane lock, mines, and barging as separate mechanics. Establish original championship rewards and scoring after confirming the reference structure.

P2 · build correctness Track generation writes invalid output before rejection

With --write, the generator overwrites workshop-track.json before running minimumFailures. A rejected radius, grade, or clearance can therefore leave the last good authored file replaced.

Rewrite action: generate in memory, validate every output, write to a temporary sibling file, then rename on success. Add one failure-path check proving that the previous bundle survives a rejected export.

tools/generate-track-path.mjs:335–339,361–364

P2 · resilience A failed car download can stop presentation startup

All four models load via Promise.all. A single rejected download rejects startPresentation, whose caller does not handle that rejection; rendering has not started yet. There is no visible retry or asset-specific failure panel.

Rewrite action: show staged loading and actionable errors, retry the failing asset, and provide a clearly temporary fallback car for development. Validate bundle manifests before release so missing assets fail the build.

src/main.ts:161–162,396,432,727–738

P2 · delivery Solo play depends on a live room server; server timing needs hardening

The application connects immediately and sends create_solo_race to the server. Practice cannot run offline or pause independently. The server advances one tick per interval callback without measuring elapsed time, and broadcasts lack application backpressure limits. Slow callbacks can stretch race time and slow sockets can accumulate queued messages.

Rewrite action: make a local race host drive the same simulation, add monotonic elapsed-time scheduling with a bounded catch-up policy, and bound network queues, room counts, and input rates before internet release.

03

A playable specification

Every lap should demand decisions.

The central loop is: read the next bend and traffic, choose a lane and speed, commit to a pass or item, recover quickly, and improve the next lap.

Input & handling

  • Provisional keyboard: A/D or ←/→ for adjacent lanes; W/↑ for acceleration; Space for item use; Escape for local pause.
  • Provisional gamepad: D-pad/stick left/right for lanes, right trigger for acceleration, face button for item, menu for pause. Bindings are remappable and are not claimed as PS2 mappings.
  • Acceleration is a 0–1 action, digital on keyboard and analog on a trigger. Verify whether braking is needed before adding it; lifting must have a deliberate slowdown curve.
  • Lane switches begin visually on the next render frame. Start tuning at 120–200 ms per transition with one short buffered edge, then measure against the reference.
  • Resolve control locks explicitly during recovery, lane-lock items and authored stunt sections. Show why a command was refused.

Risk & racecraft

  • Use authored/compiled per-lane curvature and grip limits. Overspeed builds a bounded instability meter; warnings precede failure.
  • Show lean, tyre chatter/sparks, a distinct audio cue and optional rumble before a de-slot. A UI meter supports the physical cues.
  • Class changes alter acceleration, ceiling and grip risk together. Higher voltage should demand earlier reading and sharper timing.
  • Drafting remains a measured design choice; retain only if it supports observed/reference-like overtaking. Disable it in the parity prototype until assessed.
  • Use scripted departures and reinsertion after a crash; keep authoritative gameplay constrained to the track model.

Cars & voltage

Propose twelve original bodies across six silhouette families: compact classic, long muscle coupe, stock racer, endurance prototype, open-wheel and modern GT. Each has an explicit stat definition. Three voltage tiers scale the challenge; four liveries per body yield 48 visual choices, not 48 unique handling models.

Car families and numbers are an original production target. No vehicle badges or copied bodywork are required.

Championship

Propose three cups, one per voltage tier, each using five household events. Bronze/silver/gold thresholds unlock the next cup and cosmetic rewards; event replay and quick race remain available. Prototype scoring: 10/6/3/1 points for four finishers, stable tie-break by wins then race time.

These scoring and unlock rules are proposed, not reconstructed. Keep competitive private-room car availability equal.

Opponents

Keep explicit AI decisions: lane utility, contact prediction, acceleration/lift, item use and stunt speed planning. Difficulty changes reaction delay, planning horizon and error rate; profiles obey the same rules as humans. Add seeded personalities and lane-switch hysteresis.

Verify lap-time ordering across every class and map. Do not make difficulty depend on hidden speed cheats.

Race and save flow: title → mode → car/tier → track/event → loading → countdown → race → results → retry/next event. Save a versioned local profile, cup results, unlocks, settings, bindings and personal times. Validate on load, keep a last-good backup, support export/import, and migrate only recognized versions. Time-trial ghosts store a seed, content hash and input stream.

Mode boundaries: offline races can pause and recover from a hidden tab. Online races continue on the server; pause opens an overlay and hands control to an explicit assist/bot policy. Local split-screen shares one simulation and two independent cameras/HUDs. Mixed local-plus-online seats are deferred unless explicitly requested.

This is a small proposed directory structure, not a new framework. Introduce seams when the vertical slice needs them; avoid empty modules, a general ECS, DI container or plugin system.

Core contracts

  • createRace(content, config, seed) creates a complete state.
  • stepRace(state, inputFrames, dt) returns new state and canonical events without browser/renderer APIs.
  • sampleTrack(track, section, u, lane) returns position, quaternion, tangent, curvature and route metrics.
  • LocalRaceHost drives offline/local races. The room server drives the same step function online.
  • presentRace(state, events, alpha) renders and plays feedback; it never decides a pickup, collision or finish.
  • Use plain typed data and a few functions. Keep public surfaces small; internal helpers stay with the system that owns the rule.

Track geometry and simulation must agree

Compile the center route into a dense lookup table with a continuous, designer-authored orientation frame. Use transported frames as a starting point, apply authored roll, and correct the closed-loop seam. Store quaternions and ensure tangent/frame agreement; never reconstruct an up vector from world-up at a vertical tangent.

For each lane, compile cumulative length and curvature. A car holds section/route coordinate u, lane transition, physical speed, lap/checkpoint state and effects. Convert distance to route advance through that lane's metric: Δu ≈ v × Δt / |∂P_lane/∂u|, with substeps or distance lookup across boundaries. While changing lanes, use the sampled transition path and its metric. Inner and outer lanes then cover different distances honestly, without forcing every bend to be broad.

Progress ordering uses canonical route position and validated laps; contact uses a common route coordinate plus a world-distance clearance derived from the local lane metric. Separate elevated crossings by section identity; cars on distant route sections do not collide merely because their XZ positions overlap. Swept tests must handle multiple boundaries in one tick. Off-track flight is a short explicit state with a scripted trajectory and a valid return anchor.

Fixed-step and event rules

Propose 60 Hz simulation, interpolation at render rate, bounded frame catch-up, seeded randomness and stable tie ordering. Process input → speed/route proposals → lane claims/contact → timed items/obstacles → checkpoints/finish → recovery → events. Specify exact-time priorities once; preserve swept ordering invariants from the old tests.

Replay determinism is a same-content, same-runtime target. Do not assume floating-point results are bit-identical across every browser; online authority remains the server. Hash seeds, versions and content into replay metadata.

Online responsiveness

Start with 60 Hz authority and 20 Hz snapshots; benchmark before locking rates. Sequence input frames, acknowledge the last processed frame, and replay unacknowledged local inputs for prediction. Predict movement with the same core; reconcile authoritative impacts and clear speculative effects.

Remote cars use a jitter-buffered interpolation window. Test 50/100/150 ms RTT plus jitter and stalls. WS is reliable and ordered; recovery uses full snapshots. Resync rather than extrapolating through a collision indefinitely.

Content handshake: track ID + compiled hash + simulation version + car/item definitions must match. Send immutable bundle identity once, then compact dynamic snapshots. Keep canonical event IDs stable so corrections cannot duplicate audio or rewards. Schema validators should share field definitions across client/server, with tests for every declared event; avoid maintaining unrelated handwritten shape lists.

07

Art direction and implementation

Make a kit. Then make a world.

Aim for convincing miniature racing: moulded plastic track, legible toy-car silhouettes, large household objects, controlled surface detail and warm practical lighting. Keep PS2-era clarity while using modern shading and clean presentation.

Shape language

Broad silhouettes, bevelled edges, chunky wheel arches and strong roof markings visible from chase height. Track pieces share a consistent rail/groove width, connector vocabulary and support system. Props have a few characteristic details rather than many tiny parts.

Materials & palette

Use a small library: satin plastic, brushed metal, rubber, wood, enamel, cloth and foliage. Car colours contrast against each room. Reserve emissive effects for interactive signals. Bake AO and room illumination where useful; avoid noisy textures competing with rails.

Scale & readability

Choose a virtual scale bible: one render unit = one consistent art unit, an entry car about 2.2 units long, car width ~70–80% of lane spacing. Document any physical conversion separately. Validate every asset beside the same reference car, track piece and camera.

SoundMotor loops, rail/tyre sounds, ~20–30 cues, 5 music bedsOriginal synthesis/recording plus licensed source only with documented terms. Finish one motor+music mix in the slice; expand the sound palette after gameplay tuning.

The full asset path

Brief → blockout → in-game silhouette approval → final model → UV/materials → lighting/animation → export → validation → optimization → in-game approval. A beautiful selection-card render is insufficient. Every car must pass a moving chase-camera test for wheel rotation, visibility, lane fit and readability alongside duplicate liveries.

Technical art contract

  • Source .blend, ID, author, revision and license/provenance record are retained.
  • Blender +Z up, authored forward -Y; glTF export produces game +Y up/+Z forward. Verify with one axis fixture, not remembered assumptions.
  • Transforms applied to geometry; root centered at contact plane; named wheel pivots/animation nodes remain intentional.
  • Use glTF-compatible Principled materials. Bake unsupported procedural node setups into textures or replace with supported values.
  • Use local material libraries, trim sheets and atlases; start with 512–1024 px textures, 2048 only for justified room hero/atlas assets.
  • Store dimensions, visual bounds, wheel radius, suggested gameplay envelope, materials, textures and LOD metadata in the manifest.

Export & validation

  • Retain current Blender CLI/round-trip validation and wheel-origin checks. Generalize beyond cars.
  • Check finite geometry, normals, transforms, pivots, dimensions, triangle count, material slots, texture references and named nodes.
  • Judge topology according to purpose: cars may require closed meshes; foliage cards, curtains and some scene meshes need not be manifold.
  • Round-trip the GLB through the actual loader; compare pose and material appearance. Validate animation clips and UVs, too.
  • Export individual cars and room chunks. Hash outputs, write atomically, and reject stale registry/bundle combinations.
  • Use an in-game review scene with lighting presets, rotating turntable, running wheels, lane-fit overlay and performance counters.

Retain and improve the current pipeline. The existing editable Blender sources, deterministic builds, export report and round-trip checks are valuable. Relax its blanket “no image textures” rule so the new art can use deliberately authored textures and baked lighting. Use procedural generation for consistency; artist judgement owns silhouette, composition and material quality.

Asset sourcing: create the main cars, room layouts, track kit and identity in-house. Optional third-party props or sounds require a manifest entry with creator, source URL, exact terms, attribution and modifications. Reference screenshots are observation material; build new assets, track arrangements, interface graphics and music. Concept images may help brief the art, but they do not replace editable models, textures or validation.

glTF export supports a defined material subset and can split vertices at UV/normal seams; use exported triangle/vertex/material counts for budgets. Instancing and compressed textures require compatible exporter/loader paths. See Blender glTF docs and GLTFLoader.

08

The feel is a whole system

Frame the next decision.

Camera

Use an elevated chase camera with speed-dependent lead. Sample a future route frame rather than extending a yaw vector. Blend roll deliberately through banks and inversions; use a stable horizon mode where it preserves orientation. Camera zones may adjust distance, lead and horizon behavior for tunnels, jumps and room reveals.

Sweep against simplified camera blockers, keep the controlled car visible, and prefer fading designated foreground props over sudden zooms. Show a minimum useful preview distance at the fastest tier. Reduced motion disables shake, limits FOV changes and keeps warnings readable.

Game flow & HUD

Replace the persistent room dashboard with a race-first flow. Menus use large controller-focusable choices; an online room is its own screen. During racing show position, lap, speed/tier, held item, risk warning and next event cue. Setup and official results should not consume racing viewport space.

Split-screen renders two scissor viewports with per-player HUDs and independent cameras, one shared simulation/audio world. Target two players initially, not four split views. Verify common controller pairs and keyboard conflicts.

Sound & tactile feedback

Layer motor pitch from speed/load, rail buzz, corner chatter and room-specific reverb. Build short unmistakable pickup, lock, mine, shield, crash and finish cues. Compose original music beds with restrained intensity layers; duck music under crucial warnings.

Retain the current procedural breakbeat as a prototype asset. For release, deliver mixed loopable stems/cues and source sessions. Separate music/SFX/master volume; resume audio on interaction. Treat rumble as an optional capability with a non-haptic fallback.

Accessibility & diagnostics

Provide remapping, dead-zone calibration, hold/toggle acceleration assist, reduced motion, contrast-safe item shapes, independent volumes and scalable HUD. Local menus use semantic HTML, visible focus and clear back navigation.

Development overlay: speed, route/lane metric, grip pressure, frame axes, hit envelopes, camera blockers, input age, tick time, draw calls and network correction. Keep these diagnostics out of the release player's normal flow.

Rendering policy: one main light with bounded dynamic car shadows, baked/vertex room lighting, modest ambient fill, pooled VFX, shared materials and instanced repeats. Cull room chunks hidden behind large furniture. Cap device pixel ratio by quality preset and measure actual render dimensions; two viewports multiply camera work. Add post-processing only after the full slice meets the frame budget.

Automated checks

  • Deterministic seeded replay, marker/finish sweeps, simultaneous claims, contact chains and crash ordering.
  • Frame continuity through vertical tangents, inversion and closed seams; per-lane length and speed conversion.
  • One case per item pair and control-lock boundary; all event types round-trip through the client.

  • Compiler failures preserve last-good files; all manifests and exported assets resolve.
  • Browser flow: boot, controller/keyboard setup, race, pause, results, save/reload, split-screen and four-client online.
  • Network stalls/jitter, reconnect, stale input, content mismatch, hidden tabs and asset-fetch failure.

  • Reference comparison: acceleration, lane switch, contact, each item, stunt and recovery, with explicit divergences.

  • Test keyboard plus common Xbox/PlayStation-compatible controllers, hot-plugging and two-controller identity.
  • Drive every track/voltage/car combination through automated sweeps, then sample human sessions for each distinct handling family.
