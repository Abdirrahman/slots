# Rewrite stack research

Researched 8 October 2026. Primary documentation only. **Facts** below are documentation claims; **recommendations** are engineering judgments for this project. No engine benchmark, target-device profiling, or Grooverider gameplay measurement was performed by this research task.

## Decision

**Recommendation:** retain TypeScript + Vite + Three.js/WebGL2 + native HTML/CSS, Blender → glTF/GLB, and the existing Node/`ws` server for a browser-first rewrite. Rebuild the game architecture, track data, art direction, camera, and tuning rather than changing engines as the first step. Prove this choice with one complete room circuit before multiplying content.

This recommendation is conditional on browser delivery, a small team comfortable with TypeScript, four-car races, and a constrained lane simulation. The existing `package.json` already contains `three`, `ws`, Vite, TypeScript, `tsx`, and Bun tests. Existing ADRs also select this stack and an authoritative lane simulation. These are project observations, not proof that the current implementation is adequate.

**Desktop-first fork:** re-evaluate with a Godot 4 vertical slice before commissioning all tracks. Choose Godot if the priority is a controller-led standalone game with editor-based room assembly and native deployment. Prefer Unity when the team already ships it or requires specific integrations. A desktop wrapper around the browser build is also a delivery option, but is not a reason to assume better rendering or controller behavior without testing. This fork is a product/team decision, not a claim that Godot renders this game faster.

## Minimal production stack

- **Runtime:** TypeScript game code; Three.js WebGL2 rendering; Vite client build; native DOM for menus/HUD. Keep the deterministic simulation independent of Three.js, DOM, WebSocket, and audio.
- **Network:** browser-native `WebSocket`; existing `ws` server on Node. The `ws` authors explicitly direct browser clients to native WebSocket and document heartbeat handling. [ws source documentation](https://github.com/websockets/ws). No Socket.IO, hosted game service, database, Redis, or ECS is justified for initial private four-player rooms.
- **Node pin:** begin with Node **24.21.0 LTS**, the documented latest LTS checked on the research date; pin the exact chosen version in local tooling, CI, and the production image, then update deliberately for security fixes. Node recommends production use of Active/Maintenance LTS. Recheck before implementation instead of treating this date's patch as permanent. [Release](https://nodejs.org/en/blog/release/v24.21.0), [release policy](https://nodejs.org/en/about/previous-releases).
- **Tool pin:** retain the existing package manager/test runner initially and pin its version; use the lockfile in CI. Pin Blender's selected stable version and export settings as well. `tsx` can remain a development convenience; compile/version the production server artifact.
- **New test dependency only when implemented:** Playwright for actual browser boot, lobby, race, and context/asset checks. Keep current simulation tests rather than installing a second unit-test framework. KTX2/mesh decoders are added only when their compressed assets enter the build.

## Simulation and network design

Everything in this section is a **recommendation**, with numerical values proposed for the first spike rather than measured requirements.

Use a fixed-step shared simulation (start at 60 Hz) and immutable versioned track data. Car state should cover route segment, distance, lane/transition, speed, grip/slip, power-up/effect timers, and explicit attached/airborne/derailed/recovering states. Integrate acceleration, braking, slope, corner demand, traction, collisions, jumps, and recovery as authored arcade rules. Cosmetic suspension, sparks, wheel spin, and camera shake consume simulation events without determining outcomes.

Compile authored 3D paths into per-lane arc-length tables, surface frames, curvature, grade, bank, checkpoints, and jump/landing zones. Use the same compiled route for surface geometry and simulation. Inner and outer lanes need actual length handling; avoid a flat normalized progress value that silently gives different world speeds. Preserve route/height separation at flyovers. This would supersede the current elevation-as-presentation-only ADR if adopted; it does not require rigid bodies or a general physics engine.

Share a pure `step(state, inputs, track, config)` between offline play, tests, replays, and the server. Use explicit seeds, stable processing order, input sequence numbers, and track/config hashes. A fixed timestep alone does not establish cross-runtime bitwise determinism: verify replay equivalence on the chosen runtimes and quantize authoritative values where appropriate.

The server owns collisions, pickups, laps, wins, and recovery. Clients send bounded inputs rather than positions. Start with approximately 20 Hz snapshots, local input prediction/reconciliation where needed, and interpolation for opponents. Measure under latency/jitter before introducing rollback or binary protocols. Bound message sizes/rates, reject malformed input, apply heartbeat/timeouts and stale-input neutralization, and handle reconnect with a fresh authoritative snapshot. Session-only room state can remain in memory; progression can initially be local/versioned saves. A persistent service is a later requirement only if account-backed progression is chosen.

## Art and track workflow

**Facts:** Blender exports Principled metal/rough PBR, meshes, textures, animation, cameras, and custom properties; its glTF export can use +Y up and `EXT_mesh_gpu_instancing`. Curves are not preserved as runtime track curves, so the project needs a separate route-data export. The documented GPU-instancing restrictions include shared mesh data, no children on instance objects, a common parent, and no material variation. [Blender glTF manual](https://docs.blender.org/manual/en/5.1/addons/import_export/scene_gltf2.html), [instancing section](https://docs.blender.org/manual/de/5.1/addons/import_export/scene_gltf2.html#gpu-instances).

**Recommendations:**

1. Author original miniature cars and domestic/workshop room environments with one scale convention, explicit car/track dimensions, and export transforms. Store editable `.blend`/texture sources separately from generated runtime assets. Make one reference car, one track piece, and one hero prop prove the convention before production.
2. Establish a compact modular kit: track surface/rails/supports, furniture, books/boxes, tools/toys, walls, windows, lamps, and room-specific landmark props. Use shared palettes/trim textures and instanced repeated props. Keep dynamic cars, pickups, and effects separate from static room chunks.
3. Draw original route layouts around room landmarks. Block out racing lines and camera visibility first; add tabletop climbs, shelves, overpasses, and tunnels only after gameplay tests. Similarity should come from miniature scale, room traversal, corner rhythm, and spectacle; follow the existing original-or-licensed-assets manifest policy.
4. Export a versioned `track.json` from authored curves/markers and generate the surface from those data. Export room scenery and cars as GLB with agreed names, pivots, material slots, LOD variants, and custom metadata. Validate scale, normals, checkpoints, continuity, clearance, lane topology, landing alignment, and artifact hashes during the build.
5. Use baked ambient occlusion, restrained real-time lighting, and inexpensive car grounding shadows as the baseline. Prove polished materials and readable lighting in the actual game camera. Add custom lightmap integration/post-processing only after a profiler identifies room for it; glTF export does not automatically reproduce arbitrary Blender shader graphs.
6. Validate a small export fixture in-engine whenever Blender/exporter or Three.js versions change. Track triangle counts, draw calls, texture memory, compressed download size, and load timing per asset/room. Set budgets from the measured reference room rather than assuming that polygon count alone predicts performance.

**Texture fact:** Three's `KTX2Loader` transcodes Basis textures to a supported compressed GPU format, requires a WASM transcoder, and requires `detectSupport(renderer)` before loading. Attach it through `GLTFLoader.setKTX2Loader()`. [KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html), [GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html).

**Recommendation:** ship ordinary textures during the first art proof; then adopt KTX2 for the production asset set if measured GPU memory/loading warrants it. Self-host version-matched decoder/transcoder files. Geometry compression is another measured choice; do not install Draco and Meshopt by default or compress every tiny asset indiscriminately. Dispose room geometry/materials/textures, and handle loader image resources, when leaving a room.

## Controllers, split-screen, audio

**Facts:** the Gamepad specification permits an empty device list until a controller gesture has been seen, exposes standard or unmapped layouts, and subjects access to permissions policy. It recommends polling alongside animation. [W3C Gamepad](https://www.w3.org/TR/gamepad/). Godot's browser documentation also describes browser/OS/controller mapping differences and secure-context requirements. [Godot gamepad caveats](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html#gamepads).

**Recommendations:** serve HTTPS; feature-detect input access; include “press a button to join,” stable per-player assignments, deadzones, remapping for unmapped devices, unplug/rejoin handling, and keyboard fallback. Test actual Xbox/PlayStation-class pads on the supported browser/OS matrix. Four local controllers require an explicit acceptance test; keyboard rollover and browser mappings must not be assumed. Haptics are optional enhancement.

**Fact:** Three.js supports viewport/scissor rendering into portions of a shared canvas. [Three multiple views](https://threejs.org/manual/pages/multiple-scenes.html). **Recommendation:** optional local split-screen uses one renderer/scene and 2–4 cameras, not 4 WebGL contexts. Simulate once; budget each additional view's rendering cost. Gate four-view mode on target-hardware testing and offer reduced resolution/effects if necessary.

**Fact:** Chrome's audio autoplay policy may suspend an `AudioContext` until a user gesture; the documented fix is to resume it after interaction. [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay). **Recommendation:** native Web Audio is sufficient initially: engine loops driven by speed/load, tyre slip, impacts, pickup cues, ambient room beds, and separate music/effects buses. Unlock audio from the start/join gesture; handle mute, volume, focus changes, and resumed audio. No audio wrapper dependency is yet necessary.

## Verification that fits this game

**Facts:** Playwright can use full Chromium's newer headless mode with `channel: 'chromium'`; screenshot rendering varies by OS, hardware, power mode, browser settings, and headless mode. Chrome documents GPU-backed headless workloads, subject to driver/configuration setup. [Playwright browsers](https://playwright.dev/docs/browsers), [visual comparisons](https://playwright.dev/docs/test-snapshots), [Chrome GPU testing](https://developer.chrome.com/blog/supercharge-web-ai-testing).

**Recommendations:** keep meaningful deterministic tests for lane length, braking/cornering thresholds, legal/blocked lane transitions, flyover separation, jumps/recovery, lap order, pickup lifecycle, simultaneous collisions, and seeded replays. Run a four-client server test with latency/disconnect/reconnect conditions. Add browser smoke tests that assert a real WebGL2 context, assets loaded, a nonempty rendered scene, error-free menu → lobby → race → results flow, and unsupported-graphics messaging. Never let missing WebGL silently skip the only rendering check.

Use fixed seeds, loaded-asset signals, fixed viewport/camera, and a paused simulation frame for visual baselines in one pinned CI environment. Browser automation can establish that the render pipeline runs; it cannot establish the target laptop's frame rate. Validate real target GPUs/pads in headed browsers. Agree a baseline laptop, resolution, quality preset, and split-screen player count, then measure CPU/GPU frame time, worst spikes, memory, loading, and input-to-response behavior. Begin with 60 fps as a target, not a claim or guarantee.

## Gate before committing the full rewrite

Build one polished room slice: four cars, complete braking/cornering/lane-change/derail/recovery loop, authored vertical route, all camera modes, finished car/room materials, usable controller flow, audio, and a four-client private race. Verify route/visual agreement, fair collisions, stable frame pacing, complete loading, and reconnect behavior. Capture baseline hardware measurements and player feedback. Only then freeze stack/tool versions, approve asset budgets, and create the remaining rooms/championship content.
